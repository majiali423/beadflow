# 0. 给开发 Agent 的总指令

修改代码前必须完整阅读本文件和 `AGENTS.md`。旧版照片生成、矩阵编辑器和实体板识别方案已删除，不得恢复或继续扩展。

开发优先级：

1. 真实可用和可测量；
2. 用户可控、可复核、可撤销；
3. 色号与库存准确；
4. 核心流程完整；
5. 工程质量；
6. 视觉和扩展能力。

禁止：

- 从实体拼豆板照片猜准确 MARD 色号；
- 根据截图或照片 RGB 直接断言 MARD 色号；
- 用随机值、手写固定结果或简单合成图冒充 OCR 效果；
- 将低置信度 OCR 自动写入正式材料或库存；
- 在用户未明确确认时预留、扣减或恢复库存；
- 发明 MARD 色号或颜色值；
- 在未测量时声称识别准确率；
- 静默覆盖用户修正、正式材料版本或库存流水；
- 第一版加入社区抓图、公开图纸分发、AI 自动改色或生成式推荐。

# 1. 产品定位

BeadFlow 是个人拼豆图纸与库存助手：

```text
上传已有拼豆图纸
→ 检测主网格并统计有效格与颜色簇数量
→ 用图例和代表格文字映射色号
→ 用户按颜色簇快速复核
→ 保存图纸资料卡
→ 对比个人库存
→ 生成补豆清单
→ 推荐当前库存适合制作的图纸
```

产品不自动生成图纸，也不识别实体豆板颜色。

## 1.1 主要用户

- 使用 MARD 色号、保存了大量截图图纸的拼豆玩家；
- 希望制作前知道缺哪些豆、缺多少的用户；
- 有些颜色囤积很多、有些颜色库存紧张的用户；
- 同时计划多个作品，需要合并补豆清单的用户。

## 1.2 成功标准

MVP 成功必须满足：

1. 用户能上传真实图纸并得到可复核的色号用量候选；
2. 对清晰统计栏，复核工作明显少于手工逐项抄写；
3. 所有正式色号都来自用户验证过的 MARD 221 色卡；
4. 被遮挡或不确定的内容明确要求人工处理；
5. 上传和识别绝不直接修改库存；
6. 单图和多图缺料计算准确、可追踪；
7. 同一计划不会重复预留或重复扣减；
8. 推荐能解释“够用、缺多少、消耗哪些囤积色、制作后剩多少”；
9. 所有关键算法使用真实复杂样本测试；
10. 用户数据受 RLS 保护，关键写操作有审计记录。

# 2. 产品范围

## 2.1 MVP 必须实现

- 邮箱认证和个人数据隔离；
- MARD 221 色卡和个人库存；
- PNG、JPEG、WebP 图纸上传；
- 完全重复与疑似重复图片检测；
- 自动检测主网格、行列、粗细分隔线和轻微偏移；
- 有效格、空白格和不确定格分类；
- 从格子边缘稳健采样背景颜色并进行保守颜色聚类；
- 自动寻找图例和用户手动重框；
- OCR 提取图例中的“色号 + 数量”；
- MARD 白名单校验和安全的前导零规范化；
- 原图证据、OCR 原文、候选结果和置信度；
- 人工增删改、重复项合并和逐项确认；
- 标题总数与材料合计交叉校验；
- 图纸资料卡和材料清单版本；
- 单图、多图库存检查和补豆清单；
- 待做预留、开始制作扣减、撤销和防重复；
- “现在就能做”“补豆最少”“优先消耗囤积色”三种推荐；
- 从每个颜色簇选择多个清晰代表格进行受限 OCR；
- 默认忽略空白网格，并保护真实白色和浅色豆；
- 低置信度结果按颜色簇人工确认，不要求逐格修改。

## 2.2 当前非目标

- 实体豆板颜色识别；
- 任意照片生成拼豆图；
- 精确恢复所有大图的逐格可编辑矩阵；
- 只凭显示颜色自动映射 MARD 色号；
- 自训练视觉模型；
- AI 自动替代颜色；
- 社区推荐流、爬取、交易或公开转载图纸；
- 跨品牌色卡和商城比价；
- Flutter 原生客户端。

## 2.3 尺寸和颜色数量

- 图纸资料卡记录图片中真实检测出的正整数宽、高和颜色簇数量；
- 不根据标题中的尺寸或颜色数强行切格或强行指定聚类数量；
- 标题信息只用于一致性校验；
- 第一版不承诺把资料卡转换为逐格可编辑矩阵；
- 工程防护上限只能根据内存、运行时间和真实基准确定，并必须明确提示，不能冒充产品规格。

# 3. 核心领域模型

## 3.1 PaletteColor

正式数据只从 `assets/palettes/mard221.json` 加载。色号在色卡内唯一，不允许代码内另建隐藏映射。

## 3.2 PatternAsset

```ts
type PatternAsset = {
  id: string;
  userId: string;
  sourceImagePath: string;
  sha256: string;
  perceptualHash?: string;
  sourceNote?: string;
  ocrStatus: "uploaded" | "processing" | "needs_review" | "confirmed" | "failed";
  createdAt: string;
};
```

原图默认私有，不用于公开推荐或分发。

## 3.3 PatternCard

```ts
type PatternCard = {
  id: string;
  userId: string;
  assetId: string;
  name: string;
  width?: number;
  height?: number;
  declaredTotal?: number;
  recognizedTotal: number;
  materialVersion: number;
  status: "draft" | "confirmed" | "archived";
  createdAt: string;
  updatedAt: string;
};
```

## 3.4 PatternMaterialItem

```ts
type PatternMaterialItem = {
  id: string;
  patternCardId: string;
  materialVersion: number;
  paletteColorId: string;
  quantity: number;
  rawText?: string;
  confidence?: number;
  evidenceRegion?: { x: number; y: number; width: number; height: number };
  confirmedByUser: boolean;
};
```

约束：

- quantity 必须是正整数；
- paletteColorId 必须引用真实 MARD 色号；
- 同一正式版本内同一色号最终只能有一条合并结果；
- 正式版本的 recognizedTotal 必须等于材料项数量之和；
- OCR 原文和证据区域不可因规范化而丢失。

## 3.5 InventoryItem

库存数量为非负整数，并保留 `exact`/`estimated` 可信度和可选低库存安全线。

## 3.6 PatternAllocation

```ts
type PatternAllocation = {
  id: string;
  userId: string;
  patternCardId: string;
  materialVersion: number;
  idempotencyKey: string;
  status: "reserved" | "consumed" | "rolled_back";
  createdAt: string;
  updatedAt: string;
};
```

所有预留、扣减和恢复必须通过数据库事务并写入库存流水。

# 4. 图纸识别流程

## 4.1 上传和去重

1. 校验 MIME、文件大小和可解码性；
2. 修正 EXIF 方向；
3. 计算 SHA-256；
4. 计算感知哈希；
5. 完全重复时阻止无提示重复建档；
6. 疑似重复时展示原图供用户选择；
7. 上传本身不修改库存。

## 4.2 主网格检测与切格

1. 从周期性横线、竖线和交点推断主网格边界、单格宽高与行列数，不依赖标题尺寸；
2. 同时建模粗分隔线与细网格线，防止将分组线当作额外单元格；
3. 检查网格间距稳定性、轻微偏移和边界完整性；
4. 每格保留行列、原始图像、内缩采样区域、占用状态、背景特征和文字候选区域；
5. 切格时向内缩，避免网格线进入主要颜色特征；
6. 网格不稳定时停止自动计数并要求人工确认，不输出看似完整的错误结果。

## 4.3 有效格判断与颜色聚类

1. 每格输出 `occupied`、`empty` 或 `uncertain`；
2. 综合空白模板差异、背景稳定性、文字笔画、中心与边缘纹理判断；
3. 连续性和邻接关系只作为弱证据，不得抹掉孤立格或分离图案；
4. 从四角和边缘采样，过滤文字、网格线、水印和异常高亮，再计算稳健 Lab 特征；
5. 聚类采用保守拆分，之后结合多维颜色特征、图例、OCR 和空间证据融合；
6. 白色与浅色豆单独评估；无法与空白可靠区分时进入不确定状态；
7. 主网格中的有效格数和颜色簇格数是数量统计的唯一主路径。

## 4.4 图例与代表格映射

1. 检测图例色块、色号与标注数量；
2. 图例数量只用于校验，不能替代主网格计数；
3. 图例项目与颜色簇进行允许缺失项的一对一整体匹配，禁止多个近似簇重复占用同一色号；
4. 每个颜色簇抽取多个无水印、文字完整、远离网格线的代表格；
5. 只把完整的合法色号候选纳入投票；单独的顺序数字不解释为色号；
6. 色号证据优先级为：图例与格内文字一致、多个代表格多数投票、图例单独识别、标准色表候选、人工选择；
7. 标准色表颜色相似度只生成候选，不能单独确认准确色号。

## 4.5 安全规范化

- 去除大小写和首尾空格差异；
- 只有当去除数字前导零后能唯一命中真实色卡时，才可将 `H07` 规范为 `H7`；
- `O/0`、`I/1`、`S/5` 等替换只能生成候选，不能静默确认；
- 不能命中色卡的结果保持 unresolved；
- 数量必须是正整数并设置合理上限；
- 标题、尺寸坐标、水印账号不能作为材料项。

## 4.6 人工复核

每个颜色簇展示原图位置、代表格、网格统计数量、图例/OCR 证据、候选色号、分层置信度和问题原因。用户一次确认或修改整个颜色簇，不需要逐格操作。

存在以下情况时不得生成正式材料版本：

- 未解决的非法色号；
- 非正整数数量；
- 重复色号尚未处理；
- 声明总数与识别合计不一致且用户未确认差异；
- 用户未执行最终确认。

## 4.7 一致性检查

- 所有颜色簇数量之和必须等于有效格总数；
- 图例标注数量、标题总数和网格统计只做交叉校验并明确展示差异；
- 检测同一色号是否被拆成多个簇、不同色号是否被错误合并；
- 检测未命名簇、冲突簇和不确定格；
- 网格、占用、颜色簇、色号映射分别记录置信度；
- 任一关键层级不可靠时，不得自动写入正式材料或库存。

# 5. 库存与补豆

```text
available[color] = inventory[color] - activeReservations[color]
shortage[color] = max(required[color] - available[color], 0)
remaining[color] = available[color] - required[color]
```

规则：

- 检查库存和生成补豆清单均为只读；
- 多图计算先合并同色需求，再减去当前可用量；
- 补豆清单支持复制和 CSV；
- estimated 库存必须在结果中明确标记；
- 无用户安全线时不擅自判定低库存；
- 不推荐自动替代色。

库存动作：

- **只保存**：不预留、不扣减；
- **加入待做**：创建预留，不改变实际数量；
- **开始制作**：明确确认后解除对应预留并原子扣减；
- **撤销**：在不覆盖后续操作的前提下恢复并记录反向流水。

# 6. 图纸推荐

推荐来源仅限当前用户确认过的图纸资料卡。

## 6.1 三个入口

1. **现在就能做**：所有 shortage 都为 0；
2. **补豆最少**：依次按缺少总颗数、缺少色号数排序；
3. **优先消耗囤积色**：奖励对安全线以上库存的使用，惩罚制作后跌破安全线的色号。

推荐卡必须展示：

- 缩略图、名称、总颗数、颜色数和可用尺寸；
- 是否够用；
- 缺哪些、各缺多少；
- 消耗哪些高库存色；
- 哪些色会跌破安全线；
- 制作后预计剩余。

推荐使用确定性、可解释规则，不训练推荐模型，不输出无法解释的“AI 匹配度”。

# 7. 技术架构

保留现有 Monorepo：

```text
React/Vite Web
├── 图纸资料库
├── 上传与 OCR 复核
├── 库存
├── 缺料与补豆
└── 库存推荐
        │
Fastify API
├── 图纸资料卡
├── 材料版本
├── 库存事务
└── 推荐查询
        │
        ├── Supabase PostgreSQL / Storage / RLS
        └── FastAPI CV/OCR Service
```

要求：

- 图像预处理、OCR 适配器和解析器独立于 React 组件；
- OCR 引擎可替换；
- API 不信任客户端 OCR 结果，正式保存时重新校验色号和数量；
- 推荐逻辑放在确定性 domain engine；
- 第一版推荐实时计算，不建立易失效的推荐缓存；
- 原始私人图片不写入普通应用日志。

# 11. 测试与可靠性

## 11.1 真实图纸 Golden Set

第一批使用用户提供的 13 张真实图：

- 多种尺寸，包括 20×24、24×19、44×35、47×54、49×54、54×54 等；
- 清晰和高密度统计栏；
- 深底白字与浅底黑字；
- 前导零色号；
- 水印、遮挡和贴边文本；
- 不同颜色簇数量的真实图纸。

每张 fixture 必须有人工真值、文件哈希和逐字段结果。不得只报告平均值。

## 11.2 指标

- 色号 exact match；
- 数量 exact match；
- 完整材料对 exact match；
- 漏项率；
- 误报率；
- 自动规范化正确率；
- 需要人工复核的比例；
- 单图处理时间。

第一阶段还必须逐图记录：

- 网格行列是否完全正确；
- 有效格总数误差；
- 各颜色簇计数误差；
- 颜色簇拆分或合并异常；
- 不确定格数量和需要人工确认的簇数量。

支持范围内的干净导出图目标是格子总数和各颜色簇数量完全一致。无法可靠判断的图片必须进入人工确认，不能为了提高自动通过率而输出错误结果。

第一轮是基线测量，不预设虚假准确率。进入产品集成前再根据真实结果确定最低门槛。

## 11.3 安全验收

- 非法 MARD 色号不能进入正式材料；
- 遮挡字段不能获得伪造的高置信度；
- 合计不一致必须提示；
- 重复图片和重复库存操作受保护；
- 库存不足时整个事务回滚；
- 撤销不能覆盖后续合法操作；
- 用户 A 无法读取用户 B 的图片、材料或库存。

每个 Phase 完成后运行 formatter、lint、typecheck、单元测试、集成测试和生产构建。OCR 阶段必须使用真实图片。

# 12. 开发阶段

## Phase 0：旧方案清理与规格统一

- 删除旧生成器、矩阵编辑器、实体板扫描和制作计划代码；
- 更新当前 SPEC、AGENTS、README 和架构文档；
- 停止暴露旧页面与 API；
- 只保留新图纸资料、库存和历史审计数据。

## Phase 1：主网格与颜色簇计数

- 自动检测主网格、粗细线、行列与轻微偏移；
- 切格并输出有效、空白和不确定状态；
- 提取稳健 Lab 背景特征；
- 保守聚类并检测拆分、合并异常；
- 提供网格、状态和颜色簇位置可视化；
- 用真实复杂图片输出逐图误差报告；
- 不接库存扣减，不引入新模型。

## Phase 2：图例整体匹配

- 识别图例色块、色号和标注数量；
- 与颜色簇进行允许缺失项的一对一整体匹配；
- 用图例数量与标题总数校验主网格结果；
- 冲突结果进入颜色簇级人工确认。

## Phase 3：格内受限 OCR 补全

- 每簇选择多个清晰代表格；
- MARD 白名单约束、完整色号识别和多格投票；
- 忽略顺序数字，处理水印和遮挡；
- 图例缺失时补全颜色簇名称。

## Phase 4：颜色簇复核与正式材料

- 展示簇位置、代表格、计数和多路证据；
- 用户一次确认或修改整个颜色簇；
- 保存可追踪的正式材料版本；
- 识别和复核不修改库存。

## Phase 5：库存、补豆与推荐事务

- 单图和多图检查与补豆清单；
- 预留、扣减、撤销和防重复；
- 三个确定性推荐模式与制作后余量；
- 使用真实资料卡和完整库存做事务验收。

## Phase 6：打磨与发布

- 性能、中断恢复、隐私删除和数据导出；
- 移动端、无障碍和 PWA；
- 确认不存在旧 UI、旧 API 和旧产品约束；
- 全量回归和部署验收。
